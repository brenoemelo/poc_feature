Technical Specification: Migration of AWS Infrastructure (LocalStack) to Terraform

1. Context and Objective

The objective of this document is to define the architectural standard and rules for migrating imperative deployment scripts (AWS CLI via PowerShell) to a declarative approach based on Terraform. The main target environment for local development is LocalStack, using the tflocal tool for endpoint abstraction.

2. Directory Structure (Monorepo)

To support multiple microservices (Gateway, Populator, Materials API) without duplicating code and maintaining fault isolation (blast radius), we will adopt the following structure:

/my-project
├── /src                           # API source code (.NET)
│   ├── /Gateway
│   ├── /Populator
│   └── /MaterialsApi
│
└── /terraform                     # Infrastructure as Code (IaC)
    │
    ├── /modules                   # 🛠️ REUSABLE MODULES
    │   ├── /lambda-api            # Template: IAM + Lambda (Synchronous) + CloudWatch
    │   ├── /lambda-worker         # Template: IAM + Lambda + SQS + SNS + Event Mapping
    │   └── /api-gateway-route     # Template: Resource + Method + Integration
    │
    ├── /shared                    # 🌐 SHARED INFRASTRUCTURE
    │   ├── main.tf                # Base API Gateway (Rest API), VPC, Global IAM Roles
    │   └── provider.tf            
    │
    └── /services                  # 🚀 INDIVIDUAL DEPLOYMENT (ISOLATED STATES)
        ├── /gateway
        │   ├── main.tf            # Consumes modules and resources from /shared
        │   ├── variables.tf
        │   └── provider.tf
        │
        ├── /populator
        │   ├── main.tf            # Deployment of Worker and Main API for Populator
        │   ├── variables.tf
        │   └── provider.tf
        │
        └── /materials-api
            ├── main.tf
            └── ...


3. Basic Rules and Best Practices

3.1. State Isolation (tfstate)

Rule: NEVER execute terraform apply at the root of the project.
Each folder inside /services/ and the /shared/ folder must have its own state. If the Populator deployment fails, the Gateway and Materials API must not be affected.

3.2. Referencing Files and Relative Paths

Rule: Using absolute paths (e.g., D:\Projects\...) is prohibited.
Use the native ${path.module} variable to reference the .zip artifacts generated by the .NET build.
Example: filename = "${path.module}/../../../src/Populator/PoC-Populator.zip"

3.3. Integration with LocalStack

Rule: The AWS provider must not contain fixed endpoints blocks in the versioned code.
The injection of localhost:4566 endpoints must be done transparently using the LocalStack CLI (tflocal).

3.4. Code Change Management (Zip Hash)

Rule: Always define the source_code_hash attribute in Lambdas. This ensures that Terraform only triggers a new deployment of the Lambda when the content of the .zip (.NET) file changes.

4. Implementation Blueprint: The lambda-worker Module

To exemplify the creation of a reusable component, below is the definition of the module that provisions an SNS Topic, an SQS Queue, the Subscription, and the Worker Lambda.

4.1. Module Definition (/terraform/modules/lambda-worker/main.tf)

# 1. Messaging (SNS and SQS)
resource "aws_sns_topic" "this" {
  name = var.topic_name
}

resource "aws_sqs_queue" "this" {
  name = var.queue_name
}

resource "aws_sns_topic_subscription" "this" {
  topic_arn            = aws_sns_topic.this.arn
  protocol             = "sqs"
  endpoint             = aws_sqs_queue.this.arn
  raw_message_delivery = true
}

# 2. Compute (Lambda)
resource "aws_lambda_function" "worker" {
  function_name    = var.service_name
  role             = var.lambda_role_arn
  runtime          = var.runtime
  handler          = var.handler
  timeout          = var.timeout
  memory_size      = var.memory_size
  
  filename         = var.zip_path
  source_code_hash = filebase64sha256(var.zip_path)

  environment {
    variables = var.environment_variables
  }
}

# 3. Integration (Event Source Mapping)
resource "aws_lambda_event_source_mapping" "sqs_trigger" {
  event_source_arn = aws_sqs_queue.this.arn
  function_name    = aws_lambda_function.worker.arn
  batch_size       = var.batch_size
}


5. Implementation of a Service: Populator

How the Populator service consumes the module created above.

5.1. Module Usage (/terraform/services/populator/main.tf)

# Reference to data already created in the /shared folder
data "aws_iam_role" "lambda_exec" {
  name = "lambda-role"
}

# Declaration of local variables for the Lambdas
locals {
  common_env_vars = {
    OTEL_EXPORTER_OTLP_ENDPOINT = "http://otel-collector:4318"
    OTEL_EXPORTER_OTLP_PROTOCOL = "http/protobuf"
    AWS__Region                 = "us-east-1"
    FeatureFlags__UnleashApiUrl = "http://unleash:4242/api/"
  }
}

# Worker Deployment using the Module
module "populator_worker" {
  source = "../../modules/lambda-worker"

  service_name    = "populator-worker"
  topic_name      = "population-requests"
  queue_name      = "populator-queue"
  runtime         = "dotnet8"
  handler         = "PoC.Populator::PoC.Populator.Functions.PopulatorWorkerFunction::FunctionHandler"
  zip_path        = "${path.module}/../../../src/Populator/PoC-Populator.zip"
  lambda_role_arn = data.aws_iam_role.lambda_exec.arn
  
  # Merges common variables with specific variables for this service
  environment_variables = merge(local.common_env_vars, {
    MATERIALS_API_URL = "http://localstack:4566/_aws/execute-api/material-api/prod/"
  })
}

6. Deployment Workflow (Local)

To test or deploy updates on the local machine, the team must follow this workflow:

Install the LocalStack wrapper (Once per machine):

pip install terraform-local


Spin up the Shared Base Infrastructure (First Execution):

cd terraform/shared
tflocal init
tflocal apply -auto-approve


Deploy a Microservice (Whenever the C# is compiled):

cd terraform/services/populator
tflocal init # Only the first time
tflocal apply -auto-approve


7. Referencing the Existing API Gateway

If the API Gateway was created in the /shared folder (step 2 of the workflow), services like the Populator will need to register their routes in it. This is done by reading the shared state or using data sources in Terraform to find the Gateway ID (nmmdxwos2r) dynamically, avoiding hardcoding.
