# Grafana Tempo Documentation

## Overview

**Grafana Tempo** is an open-source, easy-to-use, and high-scale distributed tracing backend. In this project (PoC Material Formulation), Tempo is used as the centralized store for all distributed traces generated by our microservices.

It is designed to be cost-efficient, requiring only object storage (S3, GCS, Azure, or local disk) to operate, and is deeply integrated with Grafana, Prometheus, and Loki.

## Architecture

In this Proof of Concept (PoC) environment, Tempo is deployed in **Monolithic Mode** (Single Binary).

### Deployment Mode: Monolithic
All Tempo components run within a single process/container (`grafana/tempo`). This is ideal for development, testing, and low-traffic environments.

The components running inside the single binary include:
- **Distributor**: Receives spans from the OpenTelemetry Collector.
- **Ingester**: Batches traces into blocks and writes them to the backend.
- **Querier**: Handles search requests from Grafana.
- **Compactor**: Manages block retention and compaction.
- **Metrics Generator**: Derives metrics from traces (e.g., service graphs).

## Configuration Details

The configuration is defined in [`docker/observability/tempo.yaml`](file:///d:/Projetos/poc_feature/docker/observability/tempo.yaml).

### 1. Protocol Receivers (Distributor)
Tempo is configured to accept traces via the **OTLP** (OpenTelemetry Protocol), matching our standard for vendor-neutral instrumentation.

```yaml
distributor:
  receivers:
    otlp:
      protocols:
        http: # Port 4318 (internal)
        grpc: # Port 4317 (internal)
```

### 2. In-Memory Ring
Since we are running a single instance in Docker Compose, we use an `inmemory` key-value store for the hash ring. This avoids the complexity of setting up a separate Consul or Etcd cluster.

```yaml
ring:
  kvstore:
    store: inmemory
```

### 3. Storage & Block Format (vParquet4)
We use **Local Storage** for this PoC to keep it self-contained. Crucially, we use the **vParquet4** block format.

```yaml
storage:
  trace:
    backend: local
    block:
      version: vParquet4 # CRITICAL: Enables TraceQL search features
    local:
      path: /tmp/tempo/blocks
```

**Why vParquet4?**
- It is a columnar format optimized for storage efficiency.
- **Essential for TraceQL**: It enables advanced search capabilities like `| select(.duration, .status)`, which allows projecting specific columns in query results. Older formats (v2, v3) have limited support for these features.

### 4. Metrics Generator
Tempo derives metrics from the incoming trace data and pushes them to Prometheus. This allows us to see "Service Graphs" and "Span Metrics" (RED method - Rate, Errors, Duration) without explicit instrumentation in the code.

```yaml
metrics_generator:
  registry:
    external_labels:
      source: tempo
      cluster: docker-compose
  storage:
    remote_write:
      - url: http://prometheus:9090/api/v1/write
        send_exemplars: true # Links metrics to specific traces
```

## TraceQL (Trace Query Language)

TraceQL is a query language designed for selecting and aggregating traces.

### Basic Queries
- **Find traces by service:**
  `{ span.service.name = "PoC.Materials.API" }`
- **Find slow traces:**
  `{ span.duration > 500ms }`
- **Find errors:**
  `{ span.status.code = "STATUS_CODE_ERROR" }`

### Advanced Queries (Structural)
- **Traces where Service A called Service B:**
  `{ span.service.name = "PoC.Materials.API" } && { span.service.name = "PoC.Costing.API" }`

### Projections (Requires vParquet4)
You can select specific attributes to display in the results table:
`{ span.duration > 100ms } | select(.duration, .service.name, .http.method)`

> **Note on `order_by`**: As of Tempo v2.7.1, the `order_by` operator is not fully supported in the TraceQL implementation used. Filtering and Selection work as expected.

## Integration Flow

1.  **Apps** (Materials, Costing) -> Emit Traces (OTLP)
2.  **OpenTelemetry Collector** -> Receives Traces -> Forwards to **Tempo** (Port 4317)
3.  **Tempo**:
    - Stores Traces in Local Disk (`/tmp/tempo/blocks`).
    - Generates Metrics -> Pushes to **Prometheus**.
4.  **Grafana**:
    - Queries **Tempo** for Traces (Explore view).
    - Queries **Prometheus** for Service Graphs (linked to traces).
